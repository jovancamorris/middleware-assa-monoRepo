01 Latar Belakang & Pembaruan Arsitektur v2.0

Evolusi standarisasi dokumen operasional SPK dan penyatuan siklus tagihan vendor ke SAP ERP.

Pada versi 2.0 ini, terdapat dua evolusi penting yang diimplementasikan di seluruh platform ASSA Atlas dan WSO2 Middleware:

Versi 1.0 (Model Lama)
❌ SPK & AP Due List Terpisah / Parsial
  • Belum ada generator XML resmi untuk SPK Final (hanya data JSON di portal).
  • Pengiriman tagihan AP Due List menggunakan method POST /api/spk/duelist berisiko duplikasi bila network timeout.
  • Root schema XML AP Due List tidak seragam dan sering menimbulkan friksi di parser ABAP SAP.
  • SPK Body Repair dan SPK Maintenance diproses dengan skema yang kaku dan rawan salah pemetaan pajak.
Versi 2.0 (Standar Baru Terpadu)
✅ SPK Final (POST) & AP Due List (PUT) v2.0
  • Endpoint Baru POST /api/v1/spk/final: Generate XML resmi mencakup 4 skenario kombinasi.
  • Migrasi ke PUT /api/v1/ap-due-list: Menjamin idempotensi penggantian state invoice vendor.
  • Root Schema Resmi <INVOICE_INBOUND_REQUEST>: Konsolidasi 1 s/d 50 SPK (MTC & Body Repair).
  • Aturan Tegas: Sub-category hanya ada di Maintenance; di Body Repair tag <SUB_CATEGORY> wajib dihilangkan.

02 Alur Integrasi End-to-End SPK Final & AP Due List

Diagram visual siklus penerbitan berkas SPK Final dan penyaluran tagihan AP Due List ke SAP FICO.

1

SPK Approved

SPK disetujui internal Atlas. User dapat memicu POST /api/v1/spk/final untuk generate dokumen XML resmi.

2

Vendor Billing

Vendor menyatukan 1 s/d 50 SPK approved menjadi satu tagihan invoice resmi ber-faktur pajak di portal.

3

Submit AP Due List (PUT)

Finance Atlas submit tagihan via PUT /api/v1/ap-due-list dengan idempotency key X-Transaction-Id.

4

Middleware & FTP SAP

Middleware memetakan G/L SAP (5000000007/8), membentuk XML INVOICE_INBOUND_REQUEST, dan transfer via FTP ke SAP.

5

SAP FB60 & Closed-Loop

SAP memposting jurnal hutang vendor (FB60/MIRO) dan menghasilkan XML balikan di FTP untuk update status di Atlas.

04 Migrasi AP Due List ke Method `PUT`

Penerapan standar RESTful Idempotency untuk penerbitan tagihan vendor ke SAP.

Lama: POST /api/spk/duelist
Mengapa POST Tidak Lagi Digunakan?

Method POST secara spesifikasi HTTP bersifat non-idempotent. Ketika pengiriman tagihan mengalami jaringan timeout atau koneksi putus di tengah jalan, client yang melakukan retry POST berisiko membuat dokumen AP Invoice baru di SAP sehingga terjadi Double Payment Risk pada nomor faktur pajak yang sama.

Baru: PUT /api/v1/ap-due-list
Mengapa Harus PUT?

Method PUT bersifat idempotent state mutation. Dokumen billing (BILLING_NUMBER) sudah eksis di Atlas dan aksi ini memperbarui statusnya menjadi tagihan siap bayar (Due List). Jika terjadi retry, middleware dan SAP akan melakukan safe state replacement / replay tanpa menimbulkan duplikasi dokumen akuntansi.

Aturan Validasi Konsolidasi Multi-SPK:
Dalam 1 dokumen tagihan <INVOICE_INBOUND_REQUEST>, sistem dapat menampung 1 hingga 50 SPK sekaligus. Nilai akumulasi dari seluruh SPK_SUBTOTAL wajib sama persis dengan TOTAL_SUBTOTAL_AMOUNT pada header, dan TOTAL_INVOICE_AMOUNT wajib sama dengan $\text{Subtotal} + \text{PPN}$.

06 Standarisasi Pemetaan G/L SAP & Error Handling

Aturan rekening buku besar akuntansi SAP dan penanganan kode kesalahan transaksi.

Komponen Item (COMPONENT) Nomor G/L SAP (GL_NUMBER) Nama Akun COA SAP Kategori SPK Terkait Contoh Pekerjaan
jasa 5000000007 Biaya Pemeliharaan Armada — Jasa Bengkel Maintenance & Body Repair Tune Up, Ganti Filter, Bleeding Rem, Ketok Panel, Pengecatan Oven
part 5000000008 Biaya Pemeliharaan Armada — Suku Cadang & Bahan Maintenance & Body Repair Oli Mesin Synthetic, Brake Pad Set, Ban Radial, Clear Coat / Compound, Spion
Kasus Error HTTP Code Error Message / Detail Solusi & Tindakan Korektif
Tag <SUB_CATEGORY> ada di Body Repair 400 Invalid category structure: subCategory not allowed for BODY_REPAIR Omit properti subCategory pada saat payload kategori body_repair.
Tag Vendor ada pada SPK Internal 400 Internal SPK cannot contain vendor party info Gunakan blok <WORKSHOP_TYPE> dan nama teknisi internal.
Selisih perhitungan $\sum (\text{Qty} \times \text{Price})$ vs Total 400 sum(details[].qty * details[].price) must equal totalPrice Koreksi pembulatan sen/desimal pada baris rincian item sebelum serialisasi.
Faktur Pajak Duplikat di SAP 422 / SAP ERR SAP_TAX_INVOICE_DUPLICATE: Nomor Faktur Pajak sudah pernah digunakan Vendor wajib merevisi nomor seri faktur pajak atau finance membatalkan invoice lama.
Resubmit Transaksi (Replay) 200 OK Transaction already processed (Idempotency Replay) Middleware mengembalikan response sukses sebelumnya tanpa menduplikasi data di SAP.

07 Manajemen Direktori FTP & Rekonsiliasi Status

Pemisahan folder transaksi asinkron antara Middleware dan SAP ERP.

📁 spk/download/
Penulis: Middleware / ATLAS | Pembaca: Job SAP SPK
Tempat meletakkan berkas XML SPK Final (4 skenario kombinasi) untuk diproses oleh modul Service & Maintenance SAP.
📁 /apduelist/download/
Penulis: Middleware | Pembaca: Job SAP AP FICO
Tempat meletakkan XML INVOICE_INBOUND_REQUEST dari transaksi PUT /api/v1/ap-due-list.
📁 /apduelist/upload/
Penulis: SAP ERP | Pembaca: Middleware Poller
Tempat SAP meletakkan XML balikan status INVOICE_INBOUND_RESPONSE setelah diposting/ditolak.
📁 /apduelist/upload/success/
Arsip Sukses
File balikan SAP dipindahkan ke sini setelah callback status ke Atlas sukses (HTTP 200).
📁 /apduelist/upload/failed/
Arsip Gagal / Reprocess
File yang gagal diproses atau gagal callback ke Atlas agar dapat di-reprocess ulang oleh worker.

Pola Penamaan Berkas Resmi

  • SPK Final XML (ke spk/download): SPK_FINAL_<COMPANY>_<SPK_NUMBER>_<YYYYMMDDHHmmss>.xml
  • AP Due List Request (ke /apduelist/download): INV-<INVOICE_NUMBER>-<YYYYMMDDHHMMSS>.xml (Contoh: INV-INV-VENDOR-2026-01-20261021144555.xml)
  • AP Due List Response (dari /apduelist/upload): RESP_AP_<STATUS>_<COMPANY>_<BILLING>_<YYYYMMDDHHmmss>.xml
